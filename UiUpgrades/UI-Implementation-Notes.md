# Machine metrics production UI implementation

Updated October 23, 2026 for the isolated handoff branch. Implements [Machine-Metrics-Production-UI-Implementation-Plan.md](Machine-Metrics-Production-UI-Implementation-Plan.md) in the existing working tree. The earlier [Dashboard-Visualization-Review.md](Dashboard-Visualization-Review.md) remains historical evidence; its results are not verification of this implementation.

## Production reads

- `MachineMetricsPanel.tsx` stays above location inventory. It reads the complete authorized placement population through `/api/assets/locations/machines/`, with `location` and `include_descendants`. It traverses every page without using inventory search or inventory pagination. Empty, malformed, changed and incomplete populations are distinguished from successful totals.
- `useMachineMetrics.ts` composes existing per-machine health summaries and machine-filtered maintenance projections. Concurrent reads are bounded to four per section. Per-machine results are cached and shared with contributor reads. Obsolete requests consume cancellation signals; scope changes remount investigation selections and cannot display another location's counts.
- Health uses `MachineHealthSummary` and the existing health badges and observation-time renderer. Critical anomalies retain the backend's condition even when signals are stale. Monitoring configuration, stale signals and degraded data remain separate from condition. A failed read cannot appear as an unconfigured machine.
- Open and overdue work come from `/api/aichat/ui/maintenance-metrics/`. Counts are added only across distinct machines. Draft/inactive exclusions, lifecycle definitions, overdue calculations and reporting dates belong to the production service. Different reporting dates/timezones or incomplete responses fail the aggregate instead of producing a partial total.
- Contributor browsing selects a machine and open/overdue metric, then follows the production API's contributor offsets. The authoritative count, current row count and offset are visible. Contributor paging never changes the aggregate totals. Lifecycle labels and work-order references remain readable.
- Query identity contains host, user, authentication and authorization generation, physical scope, machine, metric and contributor offset. Current-state reads use the service's reporting clock; no browser-local due-date calculation is introduced. Reads refresh through the existing read policy. On denial, reads stop, outstanding requests are canceled and earlier payload caches are deleted. Explicit recovery resets those queries; a failed observer cannot create a removal/refetch loop.
- `maintenanceMetricsRead.ts` extracts the existing production maintenance response contract and parser for shared use. Dashboard IDs, saved selections/configuration, recorded job downtime and widget layouts remain unchanged.

## History and navigation

`MachineHistoryPanel.tsx` retains the scoped history section and downtime, observed planned time and availability values as unavailable. It explains that validated operating-time and downtime history is not connected. Its period control is disabled. It makes no history request and constructs no empty chart or synthetic series. Existing machine signal trends and their quality-gap handling are preserved.

Location/direct filters survive board, work-order detail and return links. Board cards are filtered against the full authorized placement population, without using a truncated metrics contributor page as a filter. Existing card density, task versus work-order identity, editing, keyboard/touch controls and persisted board filters are preserved. Obsolete bookmark parameters are ignored by production scope parsing; generated links carry only supported scope and navigation fields.

## Removed scaffolding

Removed the feature-specific session engine, models, HTTP adapter/routes, management commands, migration sources 0017/0018, engine-only tests, provisioning probes/scripts/runbook and ignored dataset companion. The conditional bounded-loop/feed files listed in the plan were absent. Retained migration sources have no dependency on the removed nodes. Removed generated bytecode for the deleted modules.

Shared startup/task/location files were edited only to remove the engine hooks. Production machine-scope enforcement, scope-denial fixtures/tests, the independently valid read-only setting lookup, plugin-registry test setup and unrelated sample-data loaders remain. The release-check document retains build identity, worker and local-development guidance.

No live records, database schema, migration bookkeeping or deployment configuration were modified. Deployment application of the removed migrations is **unknown**: checking a live database was outside this source cleanup. Any deployment that applied them needs a separately approved schema-retirement procedure before deploying this removal. No replacement migration or backend metrics engine was introduced.

### Reproduction

From `src/frontend`:

```sh
./node_modules/.bin/vitest run src/pages/assets/locations/machineMetrics.test.ts src/pages/assets/locations/locationTree.test.ts src/pages/assets/health/trendGeometry.test.ts
./node_modules/.bin/tsc --noEmit --pretty false
METRICS_TEST_PORT=5174 ./node_modules/.bin/playwright test --config=playwright.machine-metrics.config.ts
./node_modules/.bin/playwright test --config=playwright.machine-locations.config.ts
./node_modules/.bin/playwright test --config=playwright.maintenance.config.ts
./node_modules/.bin/lingui extract --clean
./node_modules/.bin/lingui compile --typescript
```

The machine-metrics configuration starts the installed Vite executable, or reuses a server on the selected port. Location and maintenance-widget suites use their existing port 5173 entry points. Shared chat, location and deferred-voice fixtures now import `playwright/test-lingui.ts`.
