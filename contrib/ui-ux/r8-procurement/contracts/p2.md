## B04 approval contract

Use existing `POST /api/approvals/` with `action_type: "purchase_order"`, a
stable `agent_run_id` + `tool_call_id`, `agent_checkpoint_id`, `summary`, and
`assigned_to_user_id` naming the actual approver. The operation key remains
SHA256(agent_run_id + ":" + tool_call_id); retain both input identities on retry.

The additive `payload.operation: "place_purchase_order"` prepares and, **only after
screen approval**, atomically creates goods, charges and places one native PO:

```json
{
  "operation": "place_purchase_order",
  "supplier_id": 123,
  "currency": "USD",
  "description": "Explicit representative fixture",
  "line_items": [{"supplier_part_id": 456, "quantity": "1", "unit_price": "620.00"}],
  "extra_lines": [{"description": "Freight", "quantity": "1", "unit_price": "45.00"}],
  "total": "665.00"
}
```

The numeric IDs are illustrative, never seed bindings. Header fields supported:
reference, target_date, link, contact, responsible, destination. Goods support
reference, notes, destination, target_date and discount; charges support reference,
notes, target_date, link and discount. Prices and quantities are decimal strings;
all currencies must match. The server resolves supplier/internal Part identities,
SKU, base/order unit and pack conversion, computes discounted goods_total,
charges_total and total, and rejects a different supplied total. Tax is not inferred.

Existing `create_purchase_order`, `add_po_line_item` and `issue_purchase_order`
remain available. Issue now snapshots all actual goods and charges. Existing native
internal notification semantics remain on that legacy issue operation; combined
recorded placement suppresses internal order notifications as well as sending no
supplier email. Direct executor calls without durable approval dispatch are refused.

Reuse existing open, confirm-viewed and approve endpoints. Combined placement
requires the assigned authenticated reviewer, native purchasing/line/charge grants,
and channel `screen`; no service or voice placement channel exists. The ordinary
approval revision/hash/review-evidence gates remain. Full header/goods/charge
baselines and row locks stop drift. Stable request replay returns the original
approval before state-dependent validation; changed inputs under one key return
409. Existing executions/receipts prevent duplicate PO/lines/charges on approval
replay. A failed operation requires a fresh review/key, never silent resubmission.

Execution receipt adds `charge_ids`, `total`, `currency`, `approved_by_id` and
`approved_by` to existing `order_id`, `reference`, `status`, `line_ids`, operation
and separate supplier_email_sent/email_sent/internal_notifications_possible facts.
Combined placement always returns supplier_email_sent=false and email_sent=false.
Existing ApprovalEvent/ApprovalExecution/ExecutedEffect records hold authority and
operation identity. No new Work event type is emitted by P2.

Shortage linkage keeps its existing endpoint and `purchase_order_line_id` input.
It requires Work/machine scope, manage-kit permission and purchasing read access;
first linkage requires native Placed, selected internal Part, matching active
supplier/SupplierPart, known price and sufficient unreceived base quantity after
other linked shortages. Drafts and unvalidated lines cannot become Ordered.
The shortage/PO-line pair is the stable link identity; repeated linking is a no-op.
Receipt/reservation reconciliation of these links belongs to P3.

## B05 record-only document contract

`POST /api/order/po/{pk}/recorded-evidence/`:

```json
{
  "operation_key": "persist-once-per-intended-document",
  "to": "published-recipient@example.com",
  "from_address": "actual-buyer@example.com",
  "ship_to": "Explicit authorized receiving street",
  "buyer_name": "Actual buyer name",
  "internal_ref": "Optional Work reference",
  "provenance_kind": "fixture"
}
```

Provenance is explicitly `native_record` or `fixture`. This does not assert OEM
fit, supplier acknowledgment, delivery, payment or a physical event. Required
addresses/context are never fabricated. Ship-to never falls back to supplier
address. Goods, charges, discounts, native total and identities come from the
locked native order, not the caller. Only exact rendered documents are recorded.

First response HTTP 201; matching replay HTTP 200; changed input/key collision
HTTP 409; preparation/validation errors HTTP 400. Response fields: pk, order_id,
operation_key, state=`recorded_not_sent`, supplier_email_sent=false,
attachment_state=`verified` or `corrupt`, pdf_sha256, email_sha256, recorded_at,
and context. No provider identifier, sent_at or supplier-email success is invented.

`GET` on the same endpoint lists the order's evidence metadata/context.
`GET ?operation_key=...` retrieves one result plus pdf_base64 and email_base64.
Replay resolves persisted bytes before validating the order's current state, so
later edits never change earlier evidence. Current purchasing and users.view_email
permissions are rechecked for every read/replay; POST additionally needs purchase
change authority. Existing native endpoint authentication/role checks still apply.

`context.schema_version=1` includes company_name, PO ID/reference/status/status_label/version,
issue/target dates, supplier/address, explicit delivery/buyer facts, lines,
extra_lines, subtotal, charges_total, total_price, currency, provenance_kind,
recorded_at, actor and exact email subject/body/envelope/attachment filename.
Each goods row binds native line/SupplierPart/internal Part/SKU/units/pack/quantity,
price, currency, discount and extended total; each charge has native PK, description,
quantity, price/currency/discount and extended total. Native standalone tax is absent:
it stays null, rather than declaring zero. Freight appears once as an extra row.

Storage: `order.PurchaseOrderDocumentEvidence` holds exact PDF bytes, exact MIME
email bytes, immutable render context, both SHA256 hashes, request hash, actor,
order, creation time and globally unique operation key. No file-store/provider
write occurs. There is no sender call in this service. Reconciliation verifies
stored hashes and the exact PDF attachment locally. Legacy PO generate-and-send
is refused; missing source data in other legacy document tools has no sample
fallback. Existing read-only Gmail reconciliation now verifies attachment names,
MIME types, hashes and multiplicity rather than leaving every attachment unknown.
