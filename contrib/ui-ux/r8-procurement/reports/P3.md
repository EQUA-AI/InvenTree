## What was built

`tasks/services/maintenance_receipts.py` wraps the existing native `POST /api/order/po/{po}/receive/` action. A linked maintenance PO requires one goods line, one current shortage/job binding, the matching SupplierPart/internal selected Part and supplier, an active nonvirtual nonserialized Part, current requirement version, a nonblank batch, a permitted actual location and quantity no greater than the locked PO line remainder. External-build receipts are excluded from this narrow path. Unrelated native receipts retain their behavior.

The wrapper locks Work, Kit and the native PO/line, uses the existing native receive serializer with its batch/tracking/plugin contexts, and commits native stock, exact line-to-stock associations, immutable receipt facts and a Work command/event together. The globally unique receipt operation key and Work command uniqueness guard the effect. Exact replay checks the committed receipt before creating/validating the native serializer, so a fully received auto-completed PO returns the original HTTP 201 array. Different payload/actor/PO under the same key conflicts. A pending prior receipt must be replayed before accepting a fresh key. No fallback to newest stock or part-name matching exists.

A narrow `MaintenanceReceipt` outcome and protected `MaintenanceReceiptStock` association retain the original request/response, exact native line, shortage, actor, stock IDs and receipt-time quantities/batches/locations/statuses/expiry. The receipt event remains unchanged as reservation progresses. Receipt/PO/stock/shortage history cannot be deleted through cascading receipt references.

`transaction.on_commit` calls the separately locked continuation. It reserves only the returned stock for that receipt's current Job Kit line through `mutate_stock_allocation`; other eligible items are never falsely described as receipt allocations. Current selected Part/requirement version/quantity/mode, primary procedure hash, Work machine/customer/client binding, actor roles and machine scope are checked again. Terminal Work or nonreservable Kit states stop continuation. A failed continuation retains the physical receipt and stores attention; replaying the exact native request retries allocation without receiving again. No Materials/GET/refresh path invokes it.

The exact linked shortage becomes partial or received only when receipt stock actually contributes valid fulfillment; full fulfillment sets `resolved_at` and derives Kit readiness in that transaction. Ordered/requested/partial links are preserved, with no duplicate open row beside them. Unrelated stock cannot mark a procurement shortage received. Unlinked obsolete demand is retained as canceled history. Reserve, reconcile and release calculate need from active **plus consumed** allocations for the currently selected Part. Reconciliation preserves staged/released lifecycle positions and terminal Kit history. Release of an already released allocation returns that same terminal row, keyed by allocation identity.

The shared allocator checks logical OK (including OK-derived native custom statuses), current in-stock/release state, selected Part, active/nonvirtual identity, expiry and native item/location ownership. Structural/external locations are rejected; generic existing unlocated stock remains governed by native behavior, while this receipt path requires an actual destination. Attention/damaged/returned/held/expired stock is not usable. All cross-domain commitments are recomputed under the stock lock. Extending an allocation subtracts its existing quantity from free availability, and every increment now has a durable Work command, fixing replay of a second key used to extend an existing row. Child operation keys are bounded hashes. Reserve/release enforce machine scope even on shared customer Work, and reserve replay rechecks authorization.

The new maintenance receive branch suppresses native receipt email notifications (`notify=False`) while keeping native tracking and plugin/event contexts. It adds no SMTP/provider calls. Generic unrelated native receipt notification behavior is retained. Supplier PDF/email preparation belongs to P2, with the owner's recorded-evidence-only decision unchanged.

## Contracts for UI and integration lanes

### Native receiving request and response

Existing endpoint: `POST /api/order/po/{po_pk}/receive/`.

```json
{
  "maintenance_operation_key": "<stable operation key, maximum 128 characters>",
  "maintenance_requirement_version": 1,
  "location": 123,
  "items": [{
    "line_item": 456,
    "quantity": "1",
    "status": 10,
    "batch_code": "<actual captured batch>"
  }]
}
```

IDs/version/status in this shape are examples only; resolve actual native values. Both added fields are optional/write-only for generic native schema compatibility and required by the maintenance wrapper. `maintenance_requirement_version` is **JobKitLine.version**; it is separate from Work lifecycle version and Kit.version. Existing manual `job-kit/reserve/` still expects Work lifecycle version.

Success and exact replay: unchanged **HTTP 201 `StockItemSerializer[]`**, with receipt-time response fields/IDs preserved even after later stock changes. Do not read an object envelope or manufacture a new key on timeout. Persist the exact intent before submit, reconcile Job Kit receipt readback after reload, and resubmit its stored request with the same key and receiving actor. Correcting an invalid uncommitted request may use the same key; a committed request cannot change. Invalid input returns 400, changed intent/version/binding/quantity/pending-operation conflict 409, unauthorized roles/machine scope 403, disabled linked Job Kits 404.

### Authorized receipt readback

Existing `GET /api/tasks/work-orders/{work_pk}/job-kit/` adds `receipts: []`. No new receipt route. The array is empty without **both stock view + machine authority and purchase_order view**. GET never reserves stock. Each entry has:

- `id`, `operation_key`, `event`, `kit_line`, `purchase_order_line`, `shortage`, `actor` (native integer IDs except the operation key).
- `request`: exact persisted native request, for recovery without reconstructing a changed body.
- `recorded_at`, `continued_at` (ISO timestamps; latter nullable).
- `received_before`, `received_after` (decimal strings in supplier order units).
- `stocks`: immutable `{stock_item, quantity, batch, location, status, status_custom_key, expiry_date}`; quantity is a decimal string in native base units, expiry is nullable ISO date.
- `reservation_state`: `pending | attention | allocated`; `reservation_code`: empty on allocation, otherwise a stable cause such as `RECEIPT_STOCK_NOT_RESERVED`, `MAINTENANCE_RECEIPT_CONFLICT`, `JOB_KIT_NOT_EDITABLE` or `RESERVATION_FAILED`.
- `allocation_ids`: actual matching allocations; receipt does not imply issue, consumption, fit or Closeout.

`pending` means the receipt committed but continuation has not completed. `attention` is a retained physical receipt with an unresolved reservation result. Recovery is exact POST replay, never GET mutation. `allocated` is the durable continuation outcome; current custody must still be read from native Job Kit allocations. P1's shared read adapter can join these models/facts without copying a new stock FSM. The protected association is canonical when looking up a PO line's received stock; native StockItem has no PO-line FK.

### Append-only events / commands

- `PROC_RECEIPT_RECORDED` / `maintenance_receive`: metadata `operation_key`, `po_line`, `kit_line`, `shortage`, decimal-string before/after received totals and exact stock fact snapshots. Its event actor/created_at are actual recording facts.
- `PROC_RECEIPT_ALLOCATED` / `continue_maintenance_receipt`: metadata `receipt_id`, `operation_key`, `po_line`, `kit_line`, `allocation_ids`, `stock_ids`.
- `mutate_stock_allocation` Work commands retain each allocation increment's request hash and allocation ID; successful replay returns that original allocation row, including terminal state.

Both event values fit the native 40-character limit. Receipt metadata in the generic Work audit serializer is redacted to `{receipt_visible: false}` when stock/machine or PO read authority is absent. No event key alone is treated as uniqueness.
