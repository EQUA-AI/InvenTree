## Contract mapping and implementation

- `repair.ApprovedRepairScope` retains immutable native versions, cause, ordinal scope text, crew/elapsed plan, failure codes, approver/time/note and supersession time. Version order supports a before/after **text comparison**. An ordinal is not a procedure-task identity; an approval note is not an explicit revision reason/evidence relationship.
- P41 `investigation_revise` Work events retain exact before/after request snapshots. The new read projection checks the owning Work/request before exposing them. It keeps request versions, purpose, next check, required artifact types/units/conditions, owner/checkpoint, constraint and original evidence IDs. It does not associate a request revision with a scope using timestamps or matching prose.
- P21 immutable applied procedure snapshots preserve instruction/resource/criterion versions and hashes. P22 materials preserve requirement/fit-basis/reservation/issue/use facts. P23 preserves execution versions, criteria and outcome events. None records the scope revision that changes their applicability. The UI links their existing owning panels and keeps those facts intact.
- `scope_revision.v1` is an additive read projection inside `prepared_package.v1`; no new endpoint, model, migration or approval stage. Plan & Safety compares retained scope versions and request revisions. Work, Diagnose, Parts and Verify show the revision notice and return link. Current/obsolete/conflicting records remain distinct; the overview does not select an older or ambiguous scope as current. Superseded versions remain reference records.
- Tasks, materials/fit/reservations, resources/competence, permissions/restrictions and verification criteria each state that the affected records are not recorded. Earlier evidence remains accessible, with its validity for a changed scope explicitly unknown. No blanket hold, evidence invalidation, reapproval, changed permit or sibling completion is created.

## Missing facts

The complete ticket is **Blocked** on a canonical link from diagnosis/finding/request revision to approved scope revision, an authored revision reason and supporting evidence IDs, exact affected execution-step/material/resource/permission/criterion IDs and versions, per-dependency reassessment/validity, and the source/effective boundary of any changed physical authority. Native execution services have no scope-revision applicability gate. The projection warns and selects current facts conservatively; it cannot claim that obsolete physical execution is prevented by the server or that unrelated evidence is valid for the changed scope. Those gaps are not satisfied by a text diff or a new generic whole-job block.
