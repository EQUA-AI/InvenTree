## Rule and security trade-off

Owner decision O24 deliberately removes the customer tenant boundary for Work. Every authenticated, active user with the native Work order view role can read customer-attributed Work, including Work naming a foreign machine, and Work with neither customer nor machine. A client grant, fallback client, or resolved maintenance scope is unnecessary for those records. Customerless Work naming a machine still requires that machine’s exact client scope; a clientless machine remains unresolved. Both the queryset predicate and the per-record check enforce the same rule. Inactive, anonymous and roleless actors receive no Work authority.

Work view does not grant add/change/delete, execution, completion, audit, stock, procedure, physical-authority, proposal confirmation or other named permissions. Proposed machine attachment/reassignment still authorizes the machine before foreign-key validation and checks the old and proposed Work (P32 contract B). Machines, Health, telemetry, repair packets and live inventory projections keep their independent boundaries. A shared Work row may expose its recorded machine identity/name and Work content; it cannot authorize that machine’s operational records. This is intentional cross-customer disclosure of Work content, including Work-owned attachments, reports and signed chat focus; deployments requiring customer-private Work must not treat the customer field as an isolation control after O24. Frozen reports and original attachments retain their recorded contents and hashes, including any recorded inventory references; those Work documents do not grant access to live Stock resources.

This review follows the repository [security policy](../../../../docs/docs/security.md) and [threat model](../../../../docs/docs/concepts/threat_model.md). It tests authenticated operator roles and supplied record IDs; trusted administrators, plugins/templates and server compromise remain outside that boundary. No issue, advisory, PR, external discussion, Azure connection or Azure environment file was used.

9. Generic step attachments bypassed Work scope on lists and used inconsistent ignored child-model permissions on details/actions.
