## Mapping, model and attribution

P20 found the native `repair.investigation.record_finding` writer overwrote findings in place. The existing stable finding id must remain for legacy consumers, while originals/corrections must survive as separate records. The Work projection reads native packet findings, diagnosis qualification and approved scope; it cannot infer expert ownership from them. O14 accepts `RepairFindingRevision` as designed, with migration **repair `0011_repair_finding_revisions`** retained.

`repair.RepairFindingRevision`: generated `id`; `finding` FK identifying the existing native current finding; `snapshot` JSON containing original id/key/category/observation/value/unit/source/snapshot id/observation time/verification/original recorder and creation/update times; nullable `replaced_by` (actual correcting actor); `replaced_at` (recorded replacement time). App paths append revisions, never edit them. A parent packet lock serializes the upsert; an exact repeat changes no revision/timestamp. ISO timestamps are parsed by the native Django field and normalized with configured USE_TZ/timezone rules before comparison, preventing false corrections from equivalent aware/naive representations. No physical/site timezone is guessed.

The current finding id remains stable, and the old snapshot is a separate attributed row. Unrelated findings retain their own status. Previously overwritten data cannot be reconstructed; no backfill invents an original observation or media link.

The P41 canonical request/artifact schema also supports corrections: `InvestigationArtifact.supersedes` references a saved artifact on the **same request**, and a new row retains the corrected typed payload/actual recorder/time. Cross-request supersession refuses. Original rows remain visible. The artifact's approved chat provenance (`source_turn_id`, `source_proposal_id`, actual selected file metadata/hash) grants no access to private chat. Every new request/artifact field and the rationale for its audit identifiers are documented in [P41](P41.md).

## O14 approved chat outcomes

Mapped the existing `ChatActionProposal` creation → native chat Approvals card → authenticated exact-preview confirmation → scoped canonical command before adding publication. Shared chat evidence now uses that existing flow, rather than a correction form or automatic promotion. The assistant can propose a typed correction or `check_result`; it cannot publish it. The technician reviews exact request/revision, kind/payload/file and any superseded id, then explicitly approves or dismisses. Only approval records the approving technician and source turn and copies a supported source-turn upload into a native Work attachment. Foreign Work/request/turn/file, changed revision/preview, scope revocation, rejection, expiry and unsupported publication leave no new shared evidence; retry returns the saved result once. Details are in P41's mapping and command table.

An explicitly approved `cannot_perform`, `disputed` or `pending` check result records its reason and leaves only that request unresolved (`cannot_perform`, `disputed`, `pending_external`). Owner/checkpoint stay absent when unknown. A later ordinary observation does not clear the blocker. Other requests/findings and Work lifecycle remain unchanged. Resolution still requires explicit owner/explanation and required final/performed artifacts, with explicit reopen before new evidence on a resolved request.

Diagnose qualifies the explanation when requests are unresolved, retains original/disputed/corrected records and sources/attribution/time, and offers scope-preserving discussion through the one existing assistant. No blanket invalidation or inferred expert handoff is displayed.

**Retention boundary:** text/value/snapshot references and approved byte fingerprints persist, but the existing `common.Attachment` provider can edit bytes/URL/ownership. PROTECT preserves a referenced row, not immutable media bytes. The new approved copy is real native attachment storage tested offline, with rollback cleanup; this is not deployed storage, original audio/photo codec, immutable retention or unindexed-media delivery acceptance. No shared media/provider change was made.
