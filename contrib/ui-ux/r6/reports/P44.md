## Mapping and implementation

The canonical Work owns `hold_reason`, lifecycle/version, typed assignment and append-only `HOLD`/`RESUME` events. Existing scoped `POST /api/tasks/work-orders/<id>/hold/` and `.../resume/` use expected version and idempotency key, `tasks.execute_workorder`, native readiness checks and the deployment flag. A repair packet owns its Work lifecycle and rejects these standalone commands. There is **no** site-required assignment-acceptance flag, accepted-assignment/handover record, acceptance action or escalation/delivery receipt in this checkout. Assignment and request ownership are not acceptance.

`work_continuity.v1` adds an actor-aware, read-only overview projection. It returns attributed hold/resume history, a matching hold event only when reason/status/version provenance agrees, and availability of the existing standalone commands. A legacy scalar hold does not borrow a different event's recorder/time. Unknown site acceptance, current physical/service state and cross-crew authority remain unavailable. No model, migration, site policy or new endpoint is introduced.

The Work continuity brief assembles the six operational handoff questions from saved facts: hold reason/actor/time, current recorded assignee, exact pending request IDs/versions, owners, required conditions and checkpoints, source material requirements with links to P22 movement records, saved energy-control/gate records, maintenance-account text where supplied, and visible native work dependencies with separate owner/lifecycle/version. Original evidence and P43 scope context remain linked. Plan & Safety shows recorded holds/request constraints without turning every unresolved request into a whole-job block. History supplements native Activity with attributed hold/resume events.

Authorized standalone Hold/Resume updates only the Work record. One retained actor/host/Work operation is coordinated across tabs using the existing browser facilities, and an uncertain outcome reconciles that same endpoint/body/key/version. A later refusal cannot disprove an earlier save. Stale/refused intent needs a fresh authorized overview read before replacement. A malformed receipt cannot become success; a pending command survives reload. These actions do not accept ownership, resolve requests, release physical restrictions or complete a related order.
