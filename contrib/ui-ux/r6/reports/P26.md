## Packet contract gap

`RepairPacketClose.post` returns serialized packet data, `ok`, Work id and lifecycle status, rather than P25's exact command receipt (key, event, next version and closeout id). The service itself has idempotency, but the legacy form does not carry a durable caller operation. Native readiness deliberately reports packet ownership, and capture creation/acceptance deliberately rejects packet-owned Work. Rebinding that Work to the standalone command would bypass the existing ownership boundary.

Consequently this report does **not** claim a prepared packet account, packet voice/capture forwarding, P25-style uncertain recovery for the legacy packet form, or complete packet/UI20 consolidation. Those need a mapped extension to the existing packet receipt/readiness/capture contracts and offline tests. No replacement controller or endpoint was invented. This is an explicit incomplete boundary, not a claim that external acknowledgement or physical authority exists.
