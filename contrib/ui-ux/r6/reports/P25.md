## Mapping

- Owner: `CloseoutPanel`, mounted only for `canonical_commands_enabled && !repair_packet` by `WorkOrderDetail`. Packet work retains its native packet route. No second completion command or endpoint will be added.
- Readiness: GET `tasks/work-orders/:id/readiness/?action=complete`, query identity `['work-order-readiness', id, 'complete']`; server blockers/warnings remain authoritative. Lifecycle/version are read from the work overview, not inferred from readiness or form state.
- Completion: POST `tasks/work-orders/:id/complete/` (`WorkOrderComplete`, `CompleteCommandSerializer`, `services/closeout.complete_work_order`). Requires expected_version, idempotency_key, action, result, verification_summary; accepts cause, follow_up(_required), downtime_minutes, capture_id. Capture required fields must match reviewed decisions. Active captures are governed by native readiness, never bypassed.
- Target: internal AIMMS WorkOrderCloseout and, when a machine exists, one AssetMaintenanceRecord in the same atomic transaction, plus kit release and lifecycle transition. This is not external CMMS/ERP acknowledgement, physical return or authority to operate. No external writeback contract/provider was found.
- Receipt: CommandResult includes work_order_id, event_id, command, lifecycle_status/version, correlation_id, idempotency_key and metadata.closeout_id. Its matching COMPLETED event contains the recorded timestamp. Only a validated matching receipt confirms this operation.
- Replay: exact POST with original version, original payload and original key replays the command ledger before version/readiness checks. Request hash includes actor, command, work/version, closeout hash and optional capture id. Changed intent with the same key returns IDEMPOTENCY_CONFLICT; the controller conservatively treats this as uncertain and retains the original operation. HTTP scope lookup precedes the service; the standalone service checks exact replay before its version/permission/packet checks. Packet routes have their own guards and are not rebound here. A denial after timeout does not prove the original never committed.
- Reconciliation: exact replay of the original command, followed by the existing scoped event read for its original time; no lookup-by-key route is invented. Network/5xx/invalid receipt remains uncertain. Do not generate a fresh operation while uncertain. A current completed overview alone does not prove this operation succeeded.
- Effects: GET closeout/effects exposes notification and optional memory_draft; pending/retryable/failed/outcome_unknown are follow-up states, not external maintenance update success. No effect is a physical/operating-service assertion.
- Shared readings: canonical `['closeout-readings', id]` and the readiness key must be shared with Verify & Return. Final update never creates physical readings.

## Built

- Replaced the old `complete()` closure (which minted a UUID on every click) with `useWorkRecordUpdate`. There remains one standalone POST path, owned by Closeout. The report receives that controller's state; report opening/downloading creates no controller or command.
- Each intent freezes the native version, key and all completion fields, including reviewed capture id. Persisted operation state is keyed by API host, actor and Work id. Reload restores pending as uncertain; it never auto-submits. Report text retains the original operation's fields even after reload.
- Same-origin tabs serialize execution through Web Locks, re-read the stored operation under that lock, and share updates through storage events. A browser without coordination cannot submit. These are implementation mechanisms, **not verified multi-tab acceptance**; browser execution is blocked.
- Pending blocks duplicate submission. A matching `200` committed receipt must name this Work/key/command, expected next version, event and closeout id. Queued, malformed or unrelated responses remain uncertain. Recorded time comes from the matching native audit event; unavailable time says “Time not recorded”, never the browser clock.
- Failure retains the account and original identity. Stale offers latest-record review and displays retained versus latest saved account values; deliberate replacement uses the reviewed latest version and clears stale local field overrides. Uncertain only offers checking the original update. A refusal during uncertain recovery cannot prove the earlier commit failed and cannot unlock a fresh operation.
- Releasing a refused operation is also serialized and checks the current stored key/status, so another tab's pending/uncertain operation cannot be erased by a stale local view.
- Live actor, authorization generation and API host are rechecked before late responses affect state. No read or write bypass was introduced server-side.
- Success is a concise notification and persistent status; no proof step or receipt modal. An already completed Work offers no new completion action. Notification/learning effects remain explicitly separate follow-up records.

## Coordinator follow-up — refusal after an uncertain update

The coordinator ran S6 outside this sandbox: **32 passed / 2 failed**, with the same refusal test failing on desktop and phone at `commands[1].body`. No browser execution was repeated here.

**This was a test synchronization bug, not a missing replay in the controller.** The supplied failing traces prove that both projects sent **two** completion POSTs: first an aborted request, then a **403** response, with byte-equivalent request payloads. The second POST started after the test had already begun checking the uncertain-state text. The initial timeout and refused replay deliberately share the message “original update remains unconfirmed”, so the original text assertion could pass on the first timeout's state and reach `commands[1]` before the second route callback ran.

Evidence was inspected offline from the coordinator's traces under `/private/tmp/aimms-r6-s6-browser/`; a summary with hashes, request counts/statuses, payload-equality checks and timing is saved at `data/devscratch/r6-s6/P25/follow-up/coordinator-trace-review.json`. The JSON is derived from existing traces; it does not launch a browser.

`useWorkRecordUpdate.ts` and `workRecordUpdate.ts` already follow the mapped contract: an uncertain saved intent takes precedence over a new intent, the exact original payload/key/version is POSTed again, and any refusal while recovering retains `uncertain`. Neither controller file needed changing in this follow-up.

**Spec fix:** `tests/s6/pui_final_update.spec.ts` now gates the second response, waits for exactly two recorded commands, observes the pending “Checking update status…” state, and compares the full replay payload with the original. Only then does it release and await the 403 response. It subsequently waits for the state transition back to uncertain and verifies that neither a new Update action nor “Use reviewed account for a new update” appears. The test's requirement to send the original operation remains intact and is asserted more strongly.
