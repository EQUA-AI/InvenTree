# P18 (UI11) — Handled by AIMMS on the Work panel

**Stream:** s4-work. **Date:** 19 October 2026. **Status: built and tested against fixtures and an offline backend; operational acceptance remains open.** This is not R6 acceptance; the A07 operational, real-login and deployment gates stay open.

Screens 26, 27 and 63. Acceptance group A07 (A07.2, A07.3).

## What was built

- **Backend projection `handled_actions.v1`** (`tasks/work_execution/handled.py`), added to the work-order overview, so the Work page still renders from one read. It lists only actions that left a durable record:
  - repair packet preparation runs (`RepairPacketGenerationRun`): running, succeeded or failed;
  - the packet event that created this very work order (`work_order_created` with `metadata.work_order_id` equal to this work);
  - non-manual maintenance-account extractions from a technician narrative (`CloseoutProposal` with a named non-manual extractor), plus narratives still being extracted (`CloseoutCapture.status == 'extracting'`);
  - closeout follow-ups (`CloseoutEffect`: notification and learning draft).
- **What a row carries.** Each row has a state, the source's own status, times, the source record id, a trigger where one is recorded, a structured saved result and a link to the result.
  - States are completed, active, queued, failed or unknown. Pending, leased and retryable effects are queued, not running; only dispatching is active. `outcome_unknown` is never upgraded to handled.
  - Results hold only recorded counts. Model confidence, chat turn ids and error/stack text are deliberately left out.
- **Disabled sources.** Closeout drafting follows the closeout API's gate (`AIMMS_WORK_ORDERS_ENABLED` and `AIMMS_CLOSEOUT_WIZARD_ENABLED`); follow-ups additionally require `AIMMS_CLOSEOUT_EFFECTS_ENABLED`. `sources` reports which families were read, not applicable or not enabled, so an empty list never means "AIMMS did nothing".
- **Read-only.** The projection only reads. The strengthened review test enables both closeout branches and seeds a running run, extracting capture, proposal and pending effect. It compares every persisted field in seven ledgers across two reads, plus packet `generation_status`; the original count-only check did not prove this.
- **Frontend `HandledByAimms`** on the Work panel (`execution/HandledByAimms.tsx` with the pure `execution/handledActions.ts`):
  - It shows "AIMMS is handling" for active rows and recorded results newest first: six rows, then "Show all activity (n)".
  - Count badges appear only when at least one source was read and are recomputed from the rows. A served count that disagrees with the rows makes the projection unsupported, so a badge can never disagree with its list.
  - Saved-result links go to the native repair packet page, or to the owning panel of the same Work (Parts or Closeout).
  - Each row has a Details disclosure for screen 63: trigger, source record, saved result, recorded status, started and finished times, attempts, and "Next owner: Not recorded" for anything not completed.
  - A server without the projection gets "not supplied … Nothing here means AIMMS did or did not act".
  - There is no Generate, Assign or Accept action anywhere.

## Captures inspected and fixed

These were inspected at desktop and phone, in light and dark: recorded rows, open detail, states (dark), and the successful empty state.

- **Strict-mode duplicates.** The collapsed details were kept mounted, so each result string existed twice and assistive technology would see hidden copies. The collapse now unmounts when closed, and `aria-controls` is set only while open.
- **Failed rows.** A failed row's detail showed its explanation as the "Saved result". Follow-up wording now says "No confirmed result", so an unknown effect is not asserted to have had no effect.
- **Phone layout.** On phones the state badge and time wrapped to the right edge under the text. The group no longer right-justifies, so on a wrap it sits under the text.
- **Dark mode.** The orange note at the foot of the card was a heavy block in dark mode. It is now neutral; the state badges already carry the colour.
- **Harness only.** Full-page captures taken after scrolling showed the sticky production header mid-page. Captures now start at the top. No product change.
- **Pre-existing, unchanged.** The native Board-cards table text is clipped inside its own horizontal scroller on phones. This is native behaviour and was not touched.

## Open items and blocked facts

- **No system-versus-human actor on `WorkOrderEvent`.** Events with no actor are not listed as AIMMS actions, because they may come from migrations, admins or other system paths. *Missing fact: an attributed automation actor/source on work events (D05).*
- **Generation-run trigger.** The run has no actor or trigger field, so Trigger reads "Not recorded". When the packet event recorded the requesting person, the created-work row shows "Requested by …".
- **Executed chat action proposals** (`ChatActionProposal.target_work_order_id`) are owner-only chat records and are not projected onto a shared Work page. *Missing decision: whether confirmed chat proposals count as Work-visible AIMMS actions, and under what privacy rule.*
- **Not in this ledger:** risk findings linked by `source_model`/`source_id`, job kits and assignment. They are human-actor records, have no work link, or have no persisted rationale.
- **Next owner** for failed or unknown actions is not recorded by any provider.
